# 12. 依存の方向

Step 5（UI）の設計で出てきた「部品同士をどうつなぐか」「どちら向きに依存させるか」のまとめ。
設計そのものは [11_UI設計.md](../11_UI設計.md) にある。

## 1. 「つなぐもの」は2種類ある

UI の最初の設計では、DB と画面の間に `LibrarySource` を挟む予定だった。
「2つのものをつなぐ」ので中間テーブルに似て見えるが、別物。

| | 中間テーブル（`asset_tags`） | アダプター（`LibrarySource`） |
|---|---|---|
| どこにあるか | DB の中 | Python のコード |
| つなぐもの | **データの行**同士（アセット X とタグ Y） | **型**同士（`AssetRecord` と `BrowserItem`） |
| 数の関係 | 多対多 | 1件 → 1件の変換 |
| なぜ必要か | 1つのマスに値は1つなので、多対多は別のテーブルで表すしかない | 2つの部品が別々の型を使っていて、そのままではつながらない |

アダプターの中身は「呼ばれたら下の層を呼び、結果の型を変えて返す」だけ。

```python
class LibrarySource(ItemSource):
    def load(self, category, force=False):
        with AssetLibrary(self.db_path) as library:
            records = library.find_assets(asset_type=category)
        return [record_to_item(r) for r in records]   # AssetRecord 1件 → BrowserItem 1件
```

### アダプターを挟む理由と、今回やめた理由

| 挟む理由 | 今回 |
|---|---|
| `library.py` を UI（PySide6）に依存させないため | **今も必要**。ただし画面が `AssetRecord` を直接読めば、アダプターがなくても守れる |
| UI 部品（キット）を別のツールと共有できるようにするため | **不要**。別のツールと共有しないので、キットを Megascans 専用に作り変えた |

汎用にするための層は、共有しないなら手間が増えるだけ。必要になるまで作らない。

## 2. 依存は一方通行にする

```
ui/          画面
  │  import してよい
  ▼
library.py   API（SQL はここだけ）
  │
  ▼
db.py        接続とスキーマ
```

- 上の層は下の層を import してよい。下の層は上の層を import しない。
- こうしておくと、`library.py`・`scanner.py`・`db.py` は画面を知らないまま動く。スキャンやテストに PySide6 がいらない。
- 下の層を直しても、影響は上の層にしか出ない。直すときにどこまで見ればよいかが決まる。

## 3. 用語

| 用語 | 意味 | このプロジェクトでは |
|---|---|---|
| **レイヤードアーキテクチャ**（階層化アーキテクチャ） | 処理を層に分け、上の層が下の層だけを使う構成 | 画面 → `AssetLibrary` → `db.py` → SQLite という構成全体 |
| **依存性のルール**（Dependency Rule） | 依存は外側（画面・DB などの道具）から内側（中心のロジック）へ向け、内側は外側を知らない | 「`library.py` は `ui/` を import しない」。『Clean Architecture』（Robert C. Martin）の言葉 |
| **非循環依存関係の原則**（ADP：Acyclic Dependencies Principle） | モジュール同士の依存に輪（A → B → A）を作らない | 一方通行にしておけば、輪は自然にできない |
| **安定依存の原則**（SDP：Stable Dependencies Principle） | 変わりやすいものが、変わりにくいものに依存する | 画面はよく変わり、DB と API は比較的変わらない。だから 画面 → library の向き |
| **アダプター**（Adapter パターン） | 型の合わない2つの部品の間で変換するもの | 最初の設計の `LibrarySource` |
| **依存性逆転の原則**（DIP：Dependency Inversion Principle） | 下の層が上の層を直接呼ばず、上の層から渡された関数や型を通して呼ぶ | 下の 4章 |

「上から下への一方通行」を一番直接に表すのは**依存性のルール**。構成全体を指すなら**レイヤードアーキテクチャ**。

## 4. 下から上へ伝えたいとき（依存性逆転）

例：「更新」ボタンでスキャンしているあいだ、進み具合を画面のプログレスバーに出したい。

**やってはいけない形**：`scanner.py` が画面を import して、直接プログレスバーを動かす。依存の向きが逆になり、スキャンが PySide6 なしで動かなくなる。

**向きを守る形**：画面の側から「進んだら呼ぶ関数（コールバック）」を渡す。

```python
# scanner.py — 画面のことは知らない。「呼ばれる関数がある」ことだけを知っている
def scan(library, root, on_progress: Callable[[int, int], None] | None = None):
    for i, raw in enumerate(raw_entries):
        ...
        if on_progress:
            on_progress(i + 1, len(raw_entries))

# ui/ — 画面の側で、プログレスバーを動かす関数を渡す
scan(library, root, on_progress=lambda done, total: progress.emit(done, total))
```

`scanner.py` の import は増えないので、依存の向きは 画面 → scanner のまま。それでも通知は scanner → 画面に届く。

## 5. ルールを機械的に守らせる

約束は書いておくだけだと、いつか破られる。**import-linter** を使うと、依存のルールを `pyproject.toml` に書いて確かめられる。

```toml
[tool.importlinter]
root_package = "megascans_browser"

[[tool.importlinter.contracts]]
name = "下の層は ui を import しない"
type = "forbidden"
source_modules = ["megascans_browser.library", "megascans_browser.scanner", "megascans_browser.db"]
forbidden_modules = ["megascans_browser.ui"]
```

```
uv run lint-imports      # ルールを破る import があればエラー
```

ruff や pytest と同じように、設計の約束を毎回確かめられる。
